# Performance Baseline Pass

本轮从 `0633cb7`（Combat Map V3 / Battlefield Gameplay Pass）建立基线，工作分支 `performance-baseline-pass`。不增加玩法、地图或资产；本报告只覆盖当前单人离线 8v8 白盒版本。

## ECC onboarding 与性能依赖

- TypeScript strict + Babylon.js 8.56.2 + Vite 7.3.6；入口 `src/main.ts → Game.ts`。`Game` 同时拥有渲染循环、玩法时钟和模块生命周期。没有新增依赖。
- 8v8 为玩家 + 7 个中国方 AI 对 8 个日军 AI，共 15 个 Bot、16 个 Actor。所有模拟在浏览器主线程上运行；Web Audio 的音频渲染不计入主线程 CPU。
- `Game.step → Bot.update → perception → Combat.visible → World.blocked`；感知包含距离、视野、出生保护等过滤。开火另外验证可见性及枪口遮挡。
- `Bot.update → CombatBehavior.update → choose / route → TacticalRouteGraph`；局部战术使用现有图，局部 BFS 最多 320 次扩展，选掩体最多检查 3 个候选。
- `Bot.queuePlan → RoutePlanningScheduler → TacticalRouteGraph.findSteps`；已有每帧最多完成 1 个请求、2 ms 协作预算、64 次扩展让出、每次 tick 最多 32 个生成器步。单请求可能含两段路线，故同帧最多 2 个 search starts 不表示 2 个 AI 同时规划。LRU 路径缓存上限 512，搜索工作区复用。
- `World.move / canStand / floorAt` 依赖现有碰撞空间索引与地形；`pickStaticRay` 使用现有静态网格索引。此次测量未发现需要改变碰撞算法的证据。
- `Scene.render` 是主线程渲染提交；GPU 通过 Babylon Engine 的 timer query 单独计时。帧间隔、JS 渲染提交和 GPU 时间不可互换或相加成“总帧时间”。
- Effects、ShellCasings、MuzzleFlash 使用固定池；AudioSystem 按声音层创建短生命周期节点，每个 voice 完成或被替换时 disconnect，reset 清理全部 voice。

## 修改及不变量

1. `AIWorkScheduler` 对感知、局部战术、开火 LOS 使用 FIFO 准入：每帧上限分别为 3 / 2 / 3；共用最多 5 个 AI 的重任务额度。未完成的请求跨帧保留优先级，过期请求释放，避免固定 Bot 遍历顺序导致饥饿。路线继续使用原有独立队列。
2. 只推迟到期的重任务；移动、动画、反应计时、保护计时、拉栓、装填、射击安全检查仍使用原代码。被延迟的开火不消耗弹药，不使用旧 LOS 结果。帧调度会改变决定执行的具体帧，不能声称随机战斗轨迹逐帧相同；伤害与玩法规则没有改变。
3. 音频 mix 恰为 0 / 1 时直接连接现有地表 / 地道总线；仅在真实过渡混合时创建 3 个交叉混音 GainNode。保留空间声像、滤波、声音层、音量、混响连接和 voice 上限。不会把接近端点的混合值取整。
4. 质量档只调整渲染分辨率；MEDIUM 保持原来的缩放公式。没有改 AI 数量、更新周期、地图、雾、光照、材质、音频或效果容量。
5. `src/map/`、`src/capture/`、Match、SpawnSystem、ScoreSystem、Combat、gameConfig、player、weapons 与基线内容相同。现有战略分配（1.5 秒一次）和玩家压力分配是小规模全队记账，不执行路径搜索或 LOS，保持原规则；实际 Bot 战术/LOS/路线重任务已分帧。

## 测量方法与边界

测量机：Intel i5-12600KF、NVIDIA RTX 5080，Chrome 153.0.8010.36，Windows，WebGL2 / ANGLE D3D11。1920×1080 视口、DPR=1，头部无界面浏览器实际 GPU 渲染；并非低端显卡保证。

`tests/performance-baseline.mjs` 用真实时间驱动实际 Game.step。自动玩家通过输入移动、申请路线、瞄准射击、死亡后部署；自然胜负后重开一局，持续保留同一页面、Game、场景和 AudioContext，不重载页面，不加速模拟，不强制击杀或占点。15 秒预热后开始统计，每 30 秒一个窗口。优化前后短测各 120 秒；LOW/HIGH 各 60 秒；MEDIUM 长测 900 秒。测试按顺序执行，避免多个游戏实例抢占资源。

固定随机种子使测试可重复，但真实帧时间和分帧顺序会改变后续随机分支。短测的整体耗时差异是观察值，不应全部归因于优化，尤其未修改的渲染提交。更强的音频归因来自 `tests/performance-audio.mjs`：同一浏览器交错前后版本，丢弃前两轮预热，每种混合值各 400 次有效样本；另用 OfflineAudioContext 校验输出波形。

- CPU：Engine begin/end frame 记录回调耗时；CDP `Performance.TaskDuration` 差值 / 帧数记录浏览器主线程任务耗时。包含测量包装器及自动玩家开销。
- 模块：嵌套包装计时记录 inclusive 和 exclusive；热点排名使用 exclusive 避免子调用重复计数。感知可见性还被开火和自动玩家复用，过滤器与可见性耗时分别展示；内联目标遍历包含在 AI other 中，不能将可见性计时冒称为完整感知循环。
- GPU：LOW/HIGH/长测启用 `Engine.captureGPUFrameTime`，纳秒转换为 ms，仅收集新完成的 query。优化前短测没有 GPU 计时，因此不虚构 GPU 前后改善。
- 堆：普通窗口记录 usedJSHeapSize；预热后、每 120 秒和结束后主动 GC，比较存活堆，区分缓存预热与泄漏。主动 GC 会制造小抖动，长测不是完全无 GC 干预实验。
- 对象：统计 15 个 Bot、场景对象、固定池容量与活动项、voice、路径缓存/搜索工作区；拦截所有本项目使用的 Web Audio 工厂与 disconnect，不持有强节点引用。AudioNode 数指已创建且未 disconnect 的图节点，voice 结束后回到 9 个永久节点；不等于浏览器内部对象总数。

### 后续可接受的性能预算

以下作为同机、1080p MEDIUM 白盒的回归门槛；换硬件或增加资产必须重新测量，不能直接沿用 RTX 5080 的余量。

| 项目 | 建议预算 / 硬约束 |
|---|---|
| 帧率 / 帧间隔 | 目标 60 FPS / 16.67 ms；末段平均 FPS 相对早段下降不超过 5%；30 秒窗口 P95 间隔 ≤18 ms |
| 主线程任务 | 平均 ≤4 ms/帧；Engine 回调 P95 ≤6 ms，P99 ≤8 ms（偶发主动 GC 单独标注） |

| 路线 | 保留 2 ms 协作预算、64 扩展让出、1 活动请求；缓存 ≤512、复用工作区 ≤1；局部战术搜索仍最多 320 扩展 |
